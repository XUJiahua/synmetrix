## Project Overview

**Go Actions** is a Go-based microservice that implements just-in-time (JIT) user synchronization between Keycloak (identity provider) and Hasura (GraphQL API layer) in the Synmetrix platform. It operates as a Hasura Action handler, automatically creating user accounts in Hasura when users first log in via Keycloak without requiring full user synchronization.

### Key Purpose
- Bridges Keycloak authentication with Hasura's GraphQL schema
- Automatically creates users in Hasura on first login via `/rpc/ensure_user` endpoint
- Fetches user data from Keycloak Admin API
- Manages Keycloak tokens with auto-refresh capabilities

## Architecture Overview

### RPC-Based Action Handler Pattern

The service uses a **RPC (Remote Procedure Call) router architecture** for handling Hasura Actions:

```
Hasura Action Request
        ↓
POST /rpc/:method
        ↓
Router.Handle() [internal/rpc/router.go]
        ↓
Router looks up handler by method name
        ↓
Specific ActionHandler.Handle(c *gin.Context)
        ↓
Business logic (service) + external API calls
        ↓
Response to Hasura
```

#### RPC Request Format (from Hasura)
```json
{
  "session_variables": {
    "x-hasura-user-id": "uuid-here"
  },
  "input": {},
  "action": {
    "name": "ensure_user_exists"
  }
}
```

### Component Responsibilities

1. **RPC Router** (`internal/rpc/router.go`)
   - Routes POST requests from `/rpc/:method` to appropriate handlers
   - Supports both hyphenated (`ensure-user`) and underscore (`ensure_user`) method names
   - Returns `METHOD_NOT_FOUND` error if handler doesn't exist

2. **Action Handlers** (`internal/rpc/*.go`)
   - Implement `ActionHandler` interface: `Handle(c *gin.Context)`
   - Parse Hasura Action requests
   - Call business logic services
   - Return formatted responses or errors

3. **Service Layer** (`internal/service/`)
   - Contains business logic (e.g., `UserSyncService.EnsureUserExists()`)
   - Orchestrates Keycloak and Hasura client calls
   - Handles user data transformation

4. **External Clients**
   - **Keycloak Client** (`internal/keycloak/client.go`): Manages Service Account authentication, token refresh, user data fetching
   - **Hasura Client** (`internal/hasura/client.go`): GraphQL mutations/queries for user operations

5. **Configuration** (`internal/config/config.go`)
   - Loads environment variables (required: Keycloak credentials, Hasura endpoint, secrets)
   - Validates configuration at startup
   - Supports both Service Account auth and admin user auth for Keycloak

## Key Technical Patterns

### RPC Handler Implementation

To understand how action handlers work, examine `internal/rpc/ensure_user.go`:

1. Create a handler struct that holds dependencies (services, clients, logger)
2. Implement `ActionHandler` interface: `Handle(c *gin.Context)`
3. Parse request from Gin context: `c.ShouldBindJSON(&req)`
4. Call service layer with parsed data
5. Return response via `c.JSON(status, response)` or error via `c.JSON(status, ErrorResponse)`

### Adding New RPC Actions

See `ADDING_NEW_ACTION.md` for complete guide. Quick overview:

1. Create new file in `internal/rpc/` (e.g., `my_action.go`)
2. Implement `ActionHandler` interface
3. Register in `cmd/serve.go`: `rpcRouter.Register("my_action", handler)`
4. Add Swagger documentation as code comments (see `ensure_user.go` example)
5. Update Hasura metadata to call `/rpc/my_action`
6. Test via Swagger UI or curl

### Keycloak Client Features

- **Auto Token Refresh**: Token is automatically refreshed before expiry (managed by `client.go`)
- **Two Auth Methods**: Service Account (recommended) or admin user credentials (fallback)
- **Thread-Safe**: Uses `sync.RWMutex` for concurrent token access
- See `internal/keycloak/README.md` and `USAGE_EXAMPLE.md` for details

### Hasura GraphQL Client

- **GraphQL Mutations**: `CreateUser()`, `CheckUserExists()`, `GetUser()`
- **Query Definitions**: See `internal/hasura/queries.go` for mutation strings
- **Admin Secret**: Passed in `X-Hasura-Admin-Secret` header for GraphQL access

### Error Handling

Errors are structured and logged:

```go
// Error codes returned to Hasura
KEYCLOAK_AUTH_ERROR    // Auth with Keycloak failed
KEYCLOAK_API_ERROR     // Keycloak API request failed
HASURA_API_ERROR       // Hasura GraphQL request failed
USER_NOT_FOUND         // User not in Keycloak
USER_CREATE_FAILED     // Failed to create in Hasura
INVALID_REQUEST        // Invalid HTTP request
UNAUTHORIZED           // Missing/invalid auth
METHOD_NOT_FOUND       // RPC method not found
```

Logged as structured JSON (production) or colored console (development).

## Server Initialization Flow

From `cmd/serve.go:runServe()`:

1. Load configuration from environment variables
2. Initialize structured logger (Zap)
3. Set Gin mode (release mode in production)
4. Create Keycloak client (initializes token)
5. Create Hasura GraphQL client
6. Create UserSyncService (business logic)
7. Setup Gin router with custom logger middleware
8. Create RPC router and register handlers (`ensure_user`)
9. Mount HTTP routes: `/rpc/:method`, `/health`, `/swagger/*`
10. Create HTTP server with timeouts (15s read/write, 60s idle)
11. Start server in goroutine
12. Setup graceful shutdown on SIGTERM/SIGINT (5s timeout for outstanding requests)

## Important Implementation Details

### Token Management in Keycloak Client

- Tokens are cached and auto-refreshed internally
- `GetUser()` automatically calls `ensureValidToken()` before making API calls
- RWMutex ensures thread-safe concurrent access to cached token
- See `internal/keycloak/client.go` for implementation

### User Sync Logic

In `internal/service/user_sync.go:EnsureUserExists()`:

1. Check if user exists in Hasura
2. If exists, return user data (skip Keycloak fetch)
3. If not exists:
   - Fetch user from Keycloak Admin API
   - Build display name from first/last name, username, or email prefix
   - Create user in Hasura via GraphQL mutation
   - (Optional) Create default team asynchronously

### Display Name Building

Priority order in `buildDisplayName()`:
1. firstName + lastName (from Keycloak)
2. username (from Keycloak)
3. Email prefix (before @)
4. Default: "Unknown User"

## Performance & Resource Considerations

- **Token Caching**: Reduces Keycloak API calls for repeated operations
- **Connection Pooling**: HTTP clients reuse connections across requests
- **Timeouts**: 15s read/write timeout prevents hanging requests
- **Graceful Shutdown**: 5s grace period for in-flight requests
- **Concurrent Safe**: RWMutex protects shared Keycloak token state
- **Structured Logging**: JSON format suitable for log aggregation systems

## Security Highlights

- ✅ Service Account authentication (no hardcoded user credentials)
- ✅ Minimum required Keycloak permissions (`view-users`, `query-users`)
- ✅ Non-root Docker container (runs as appuser:1000)
- ✅ Hasura Admin Secret required for GraphQL access
- ⚠️ Action Secret validation NOT enabled by default - see `SECURITY_GUIDE.md` for production setup

### Debug Log Coverage

Debug logging captures detailed information from:

1. **Keycloak Client** (`internal/keycloak/client.go`):
   - Authentication requests (method, endpoint, status code)
   - Token refresh attempts and results
   - User data fetch requests and responses
   - Error details including response bodies

2. **Hasura Client** (`internal/hasura/client.go`):
   - GraphQL query/mutation execution
   - Query variables and full query text
   - Request/response details
   - GraphQL response data and errors
   - Status codes and response bodies

3. **RPC Handler** (`internal/rpc/ensure_user.go`):
   - Incoming request data (input, session variables)
   - User ID extraction logic
   - Handler flow and response data

4. **Service Layer** (`internal/service/user_sync.go`):
   - User existence check results
   - Data fetching from Keycloak
   - User creation steps in Hasura
   - Display name generation logic

5. **RPC Router** (`internal/rpc/router.go`):
   - Method resolution (hyphenated vs underscore)
   - Handler lookup results

### Log Levels

- **DEBUG**: Detailed information about requests, responses, and flow control
- **INFO**: High-level operation status (service start, user sync steps)
- **ERROR**: Error conditions with context
- **WARN**: Warning conditions (user not found, missing data)

### Best Practices

- **Enable debug logging during development**: Helps understand request flow and identify issues
- **Disable in production**: Debug logs may leak sensitive information (though Keycloak secrets are still redacted)

- **Check logs for API endpoint URLs**: Useful for verifying correct Keycloak and Hasura configuration

## Debugging Tips

## Hasura Integration

The service expects Hasura to have these tables:
- `users` (id UUID, display_name TEXT, avatar_url TEXT)
- `auth_accounts` (user_id UUID, email CITEXT UNIQUE)
- `teams` (id UUID, name TEXT)
- `members` (user_id UUID, team_id UUID)
- `member_roles` (member_id UUID, team_role TEXT)

Hasura Action configuration in metadata:

```yaml
- name: ensure_user_exists
  definition:
    kind: synchronous
    handler: http://go-actions:3000/rpc/ensure_user
    forward_client_headers: true
  permissions:
    - role: user
```

See `INTEGRATION.md` for complete setup instructions.
